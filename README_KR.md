# 사그라다 파밀리아 취소표 모니터

공식 예매 백엔드(Clorian)를 주기적으로 확인해서, 지정한 날짜에 자리가 열리면 알림을 보냅니다. 노트북을 켜둘 필요 없이 GitHub Actions에서 돕니다.

**자동으로 장바구니에 담거나 결제하지 않습니다.** 알림을 받고 직접 예매하시면 됩니다.

---

## 감시 대상

공식 예매 페이지의 개인 티켓 4종입니다.

| 티켓 | 상품번호 | venueId |
|---|---|---|
| Sagrada Familia (일반) | 4375 | 1 |
| with guided tour | 4374 | 1640 |
| with towers | 4443 | 3 |
| with guided tour + towers | 4779 | 1783 |

`venueId`는 상품마다 다릅니다. 틀린 venue로 조회하면 API가 **에러 대신 빈 객체 `{}`** 를 돌려주기 때문에, 아무것도 감시하지 않으면서 "표 없음"처럼 보입니다. 그래서 각 상품이 자기 venue를 들고 다닙니다.

---

## 알림이 얼마나 믿을 만한가

백엔드에는 "N명이 한 타임슬롯에 같이 들어갈 수 있는가"를 묻는 `minTickets` 파라미터가 있습니다. **이게 4종 중 2종에서만 실제로 동작합니다.**

10월 한 달 기준 이용 가능 일수를 `minTickets` 값을 바꿔가며 측정한 결과입니다.

| 상품 | mt=1 | mt=4 | mt=1000 | mt=100000 | 판정 |
|---|---|---|---|---|---|
| 4375 | 17 | 17 | 0 | 0 | 실제로 적용됨 |
| 4779 | 14 | 11 | 0 | 0 | 실제로 적용됨 |
| 4374 | 20 | 20 | 20 | 20 | **무시됨** |
| 4443 | 19 | 19 | 19 | 19 | **무시됨** |

4374와 4443은 10만 명이 한 슬롯에 들어가느냐고 물어도 "가능"이라고 답합니다. 반면 4375는 특정 날짜에 148명까지 "가능", 149명부터 "불가능"으로 정확히 끊깁니다. 날짜별 상한이 100~190명대로 나오는데, 이는 하루 전체 인원으로 보기엔 너무 작아 **한 타임슬롯 정원**으로 해석됩니다.

모니터는 이 특성을 **매 실행마다 다시 탐지**합니다(`minTickets=100000`으로 찔러봄). 백엔드가 고쳐지면 자동으로 더 강한 알림으로 승격되고, 반대로 망가지면 자동으로 조심스러운 알림으로 내려갑니다.

### 알림 3종

| 제목 | 의미 |
|---|---|
| `4 TICKETS CONFIRMED` | 한 슬롯에 4명 확정. 4375 / 4779에서만 가능 |
| `Opening (size unverified)` | 날짜는 열렸으나 인원수 미확인. 1자리일 수도 있음 |
| `Only 2-3 seats per slot` | 가장 좋은 슬롯도 2~3명. 분할 예약 검토 |

한 실행에서 여러 날짜가 열려도 **알림은 1통으로 합쳐서** 보냅니다. 제목에는 가장 좋은 소식이 올라옵니다.

## 알림 경로

| 경로 | 제한 | 외부 의존 |
|---|---|---|
| **GitHub 실패 메일** | 없음 | 없음 |
| ntfy 이메일 | 무료 계정 5통 | ntfy 계정 + 토큰 |
| ntfy 푸시 | 없음 | ntfy 앱 |

표가 발견되면 **실행을 일부러 실패 처리**합니다. GitHub이 워크플로 실패 시 계정 메일로 알려주는데, 이 경로는 횟수 제한도 없고 외부 서비스에도 의존하지 않기 때문입니다. **Actions에 빨간 X가 뜨면 좋은 소식입니다.**

ntfy 이메일은 내용이 자세한 보조 경로입니다. 무료 계정은 5통 제한이 있어서, 중복 알림 억제가 기본 6시간으로 설정돼 있습니다.

`Sagrada monitor is BROKEN` / `partially blind` 알림은 모니터 자체가 고장났을 때 옵니다. 하루 한 번 오는 `alive` 하트비트가 끊기면 실행 자체가 멈춘 것입니다.

## 설정

전부 저장소 Secret으로 넣습니다. **날짜와 메모를 소스에 두지 않는 이유는, 이 저장소가 공개이기 때문입니다.**

| Secret | 필수 | 형식 |
|---|---|---|
| `NTFY_TOPIC` | ✅ | 8~64자, 영숫자/하이픈/밑줄. 이름이 곧 비밀번호 |
| `MONITOR_DATES` | ✅ | `YYYY-MM-DD,YYYY-MM-DD,...` |
| `NTFY_TOKEN` | 이메일용 | ntfy 액세스 토큰. **만료 없음으로 발급할 것** |
| `ALERT_EMAIL` | 이메일용 | ntfy 계정에서 **인증 완료된** 주소 |
| `DATE_NOTES_JSON` | 선택 | `{"YYYY-MM-DD":"해당 날짜 알림에 붙일 메모"}` |

`NTFY_TOKEN`은 반드시 **Create access token**으로 만드세요. ntfy 계정 화면의 `Current browser session` 줄을 복사하면 며칠 뒤 만료돼서 알림이 조용히 끊깁니다.

감시는 `MONITOR_DATES`의 마지막 날짜 다음 날 정오(UTC)에 자동으로 멈추고, 워크플로 스케줄도 스스로 끕니다.

## 실행 주기

GitHub 스케줄러는 잦은 cron을 대폭 솎아냅니다. 20분 간격(하루 84회)을 요청했을 때 **실제로는 하루 8회, 약 3시간 간격**으로만 실행됐습니다.

그래서 주기를 cron에 맡기지 않습니다.

1. 한 실행이 **50분간 90초 간격으로 계속 확인**합니다.
2. 끝나면 **스스로 다음 실행을 띄웁니다**(chaining).
3. cron은 체인이 끊겼을 때 복구하는 용도로만 남깁니다.

이 방식은 실행 시간을 많이 쓰므로 **공개 저장소 전제**입니다. 공개 저장소는 표준 러너 사용이 무료입니다. 비공개라면 `POLL_MINUTES`를 줄이고 `CHAIN_RUNS=false`로 꺼야 합니다.

조절 가능한 값:

| 환경변수 | 기본 | 설명 |
|---|---|---|
| `POLL_MINUTES` | 50 | 한 실행이 감시하는 시간. `timeout-minutes`보다 작아야 함 |
| `POLL_INTERVAL_SECONDS` | 90 | 확인 간격 |
| `CHAIN_RUNS` | (켜짐) | `false`면 다음 실행을 띄우지 않음 |
| `ALERT_COOLDOWN_HOURS` | 6 | 같은 알림 억제 시간 |

## 하지 않는 것

**시간대별 정확한 잔여 좌석은 가져오지 않습니다.** 공식 사이트가 시간대 목록을 받아올 때 쓰는 `/catalog/events/available` 엔드포인트는 reCAPTCHA 토큰을 요구합니다. 그걸 우회하지 않기로 했으므로, 모니터는 **달력 수준(그날 자리 있음/없음)에서 의도적으로 멈춥니다.** 정확한 시간은 알림을 받고 직접 확인해야 합니다.

**장바구니 담기나 결제는 하지 않습니다.**

## 로컬 실행

```bash
node test.mjs
MONITOR_DATES="2099-01-01,2099-01-02" NTFY_TOPIC="..." POLL_MINUTES=1 node monitor.mjs
```

`node test.mjs`는 외부 호출 없이 알림 분류 로직만 검증합니다.
